# Agent Guide — ChunkUpload

## Project Overview

ChunkUpload is a **Proof of Concept** for chunked, resumable large file uploads. Files are split into chunks (default 5 MB), uploaded sequentially to a Go backend, stored in MinIO via S3 Multipart API, with upload state tracked in Redis. If an upload is interrupted (browser crash, network loss), it can resume from the last confirmed chunk without re-uploading data.

## Architecture

### Three-Stage Upload Protocol

```
Client                        Backend (Go/Gin)              MinIO              Redis
  │                                  │                         │                  │
  │── POST /upload/init ────────────►│                         │                  │
  │   { fileName, fileSize, mime }   │── CreateMultipartUpload ►│                  │
  │                                  │── Save(UploadMeta) ──────────────────────► │
  │◄── { uploadId, chunkSize } ──────│                         │                  │
  │                                  │                         │                  │
  │── POST /upload/chunk?... ───────►│                         │                  │
  │   (raw bytes)                    │── UploadPart ──────────►│                  │
  │                                  │── MarkChunkDone ─────────────────────────► │
  │◄── { chunkIndex, progress } ─────│                         │                  │
  │   (repeat per chunk)             │                         │                  │
  │                                  │                         │                  │
  │── POST /upload/complete?... ────►│                         │                  │
  │                                  │── CompleteMultipart ───►│                  │
  │                                  │── Delete(session) ──────────────────────► │
  │◄── { location } ─────────────────│                         │                  │
```

### Resume Flow

`GET /upload/status?upload_id=xxx` returns `next_chunk_index` and the list of already-uploaded chunks. The client skips confirmed chunks and resumes from the first gap.

## Coding Conventions

### Backend (Go)

- **Module path**: `github.com/fauzanfl/chunked-upload`
- **Layout**: Standard Go project layout — `cmd/` for entrypoints, `internal/` for private packages. No exported packages outside `internal/`.
- **Configuration**: Environment variables only, read via helper functions in `config/config.go` (no third-party config libs like Viper). Every config has a sensible default.
- **Error handling**: Errors are wrapped with `fmt.Errorf("context: %w", err)` and propagated up. HTTP status codes are derived from error message content in the handler layer (e.g. `containsSubstr(err.Error(), "not found")` → 404).
- **Naming**: Standard Go conventions — `UploadMeta` (not `UploadMetadata`), short receiver names (`s` for Service), CamelCase exports.
- **DTOs**: Request/response structs live in `models/upload.go` with JSON struct tags using `snake_case` field names and Gin `binding` tags for validation.
- **Logging**: Use `logger.Get()` (global Zap logger). Every handler logs structured fields (`upload_id`, `ip`, `chunk_index`, `duration`, etc). Development mode uses console encoder, production uses JSON.
- **Swagger**: Annotations are on handler functions using `// @Summary`, `// @Router`, etc. Regenerate docs with `swag init -g cmd/server/main.go -o docs`.
- **Middleware**: Token bucket rate limiters are instantiated per middleware function (not shared). Stale IP buckets are pruned every 5 minutes.
- **Graceful shutdown**: `main.go` listens for SIGINT/SIGTERM and calls `srv.Shutdown()` with a 15-second timeout.
- **Dependencies**: AWS SDK v2 for S3 operations, `go-redis/v9` for Redis, `gin-gonic/gin` for HTTP, `google/uuid` for upload IDs.

### Frontend (TypeScript/React)

- **Build tool**: Vite 5 with `@vitejs/plugin-react`.
- **State management**: No external state library — the `useChunkedUpload` custom hook manages all upload state via `useState` and `useRef`.
- **Upload phases**: The UI is driven by an `UploadPhase` union type: `idle` → `hashing` → `initializing` → `uploading` → `completing` → `done` (with `paused` and `error` as alternatives).
- **API client**: Plain `fetch` in `services/uploadApi.ts` — no axios or other HTTP libraries. Chunk data is sent as raw `application/octet-stream` body.
- **API base URL**: Configured via `VITE_API_BASE_URL` env var (defaults to `/api/v1`).
- **Naming**: React components use PascalCase filenames; hooks use `use` prefix; services/utils use camelCase filenames.
- **Styling**: Plain CSS in `index.css` (no CSS-in-JS, no Tailwind, no UI framework).
- **JSON field names**: API responses use `snake_case` (matching the Go backend DTOs).

## Key Design Decisions

1. **Raw body for chunks** — Chunk data is sent as raw `application/octet-stream` (not multipart/form-data) to avoid unnecessary encoding overhead and enable direct streaming to MinIO.

2. **Idempotent chunk uploads** — If a chunk is uploaded twice (e.g. client retry after timeout), the server detects the duplicate via `UploadedChunks` in Redis and returns success without re-uploading to MinIO.

3. **S3 part numbers are 1-indexed** — The client uses 0-based `chunk_index`, which is mapped to 1-based S3 `partNumber` in the service layer (`partNumber = chunkIndex + 1`).

4. **Client-side SHA-256 hashing** — The frontend computes a SHA-256 hash of the entire file before uploading (phase: `hashing`). This is optional and non-blocking — if hashing fails, the upload proceeds without it.

5. **No authentication** — This is a PoC. There is no auth layer. Rate limiting per IP is the only abuse prevention mechanism.

6. **Object key format** — Files are stored in MinIO as `uploads/{uploadId}/file{ext}`, making each upload session's object unique and isolated.

## Security Controls

| Feature           | Implementation                                                              |
|-------------------|-----------------------------------------------------------------------------|
| Rate limiting     | Token bucket per IP: 100 req/min (general), 60 req/min (chunk endpoint)     |
| File size cap     | `MAX_FILE_SIZE_BYTES` env var, enforced at init stage                       |
| MIME validation   | Allow-list in `config.go`, checked before MinIO multipart upload is created |
| CORS              | Explicit origin allow-list via `ALLOWED_ORIGINS`, never wildcard `*`        |
| Chunk size cap    | `MaxBytesReader` middleware on chunk endpoint (chunk size + 1KB tolerance)  |
